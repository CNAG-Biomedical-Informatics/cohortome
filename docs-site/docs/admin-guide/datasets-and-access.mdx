Use groups as the default way to grant dataset access. Use direct allowed users only for exceptions.

```text
dataset_root/
  clinical/
  assays/transcriptomics/
```

## Access model

Dataset access is granted through:

- visibility
- allowed groups
- allowed users

The effective rule is a union:

- visible to everyone if visibility allows it
- or visible through matching groups
- or visible through explicit direct user assignment

This is intentionally a union, not a conflict model.

:::info
Effective access is granted if any allowed path matches:

- visibility
- group membership
- direct user assignment
:::

## Groups versus direct users

The intended operating model is:

- groups are the default
- direct users are exceptions

That means:

- a dataset can be granted to a whole group such as `cnag`
- a specific user can still be granted access directly even if they have no group

This is especially important for:

- temporary access
- exceptional reviewers
- local users without group membership

## Groupless users

A user with no groups is still valid.

Such a user:

- receives no dataset access from groups
- but can still receive access through:
  - broad visibility
  - direct `allowed_users`

:::note
Groupless users are valid. They do not need to be forced into a group just to be usable in the app.
:::

## What Data Administration edits

`Data Administration` edits dataset policy, not user identity.

It currently allows admins to edit:

- `Visibility`
- `Allowed groups`
- `Allowed users`
- `In-app Query detail`
- `AI providers`
- dataset DuckDB store preparation state

User records are managed in the `Users` admin tab. Dataset cards do not edit user identity directly.

## Dataset store preparation

Dataset authorization and dataset-store preparation are separate concerns.

- authorization decides whether a user may select a dataset
- store preparation decides whether the backend has a ready DuckDB store for that dataset

The admin UI now shows dataset-store state and a matching action:

- `Prepare store` for first build, stale, or failed states
- `Rebuild store` when a store is already ready and you want to refresh it deliberately

Normal user workspace loading should reuse prepared stores rather than triggering heavy rebuilds.

## Query policy fields

The admin UI now separates Query-related policy into two concepts.

### In-app Query detail

This controls what Query may return inside Biomedical Research Navigator itself:

- `Summary only`
- `Detailed allowed`

If a workspace includes more than one dataset, the strictest selected dataset wins.

That means if any selected dataset is `Summary only`, the Query thread cannot switch to `Detailed`.

In the current product, users do not manually switch Query between `Summary` and `Detailed`.

Instead:

- the effective Query mode is applied automatically from the active workspace policy
- the Query header shows the resulting mode as read-only state

### AI providers

This controls what Biomedical Research Navigator may send to AI models/providers for Query behavior.

Current options are:

- `Detailed allowed`
- `Safe summary`
- `Blocked`

`AI providers` is a dataset-level setting, not a per-user setting.

The user's selected model provider is configured separately in `Settings`.
Admins manage the provider registry in [Model Providers](./model-providers).
Dataset policy still decides whether that provider can receive context.

For multi-dataset workspaces, the strictest selected dataset wins:

- `Blocked` overrides everything
- `Safe summary` overrides `Detailed allowed`

### Safe summary

`Safe summary` does not mean “send aggregate clinical content.”

In current Query behavior it means:

- only structural, non-clinical context may leave the backend
- semantic planning is skipped
- if the prompt needs private clinical context, the provider should answer that it lacks enough permitted context

## Effective dataset access

The admin UI also shows a `Users with access` preview.

This preview answers:

- who currently gets this dataset
- under the current local auth configuration
- after visibility, groups, and direct users are combined

This is useful because it makes the group-versus-user rule explicit instead of forcing admins to infer it.

## Current admin workflow

In `Data Administration`, admins can:

- review dataset visibility
- assign allowed groups
- assign allowed users
- choose whether Query is `Summary only` or `Detailed allowed` in-app
- choose the dataset AI-provider policy for Query
- review which current local users effectively match the dataset access policy

This means the admin policy is the ceiling, and the app applies the effective behavior automatically in `Query`.
