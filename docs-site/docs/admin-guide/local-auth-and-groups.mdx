# Auth And Groups

The current app supports local authentication and a generic OIDC mode for
external identity providers such as Dex, Google, or institutional SSO.

## Source of truth

User identity is now persisted locally in:

- `state/auth/users.json`

Environment configuration is still used as bootstrap seed data when no local user store exists yet.

Typical setup:

```bash
export COHORTOME_AUTH_MODE=local
export COHORTOME_LOCAL_USERS_JSON='[
  {"username":"admin","password":"admin","role":"admin","display_name":"Administrator","groups":["admin"]},
  {"username":"mrueda","password":"mrueda","role":"user","display_name":"mrueda","groups":["cnag"]},
  {"username":"nogroup","password":"nogroup","role":"user","display_name":"No Group User","groups":[]}
]'
```

## Auth modes

COHORTome supports three authentication modes:

- `COHORTOME_AUTH_MODE=none`
  - development fallback with a synthetic local admin user
- `COHORTOME_AUTH_MODE=local`
  - local username/password users stored in `state/auth/users.json`
- `COHORTOME_AUTH_MODE=oidc`
  - external OIDC login, with COHORTome still owning roles, groups, and
    dataset access

Optional local fallback:

```bash
export COHORTOME_AUTH_LOCAL_FALLBACK=true
```

When this is set with `COHORTOME_AUTH_MODE=oidc`, the login page shows both the OIDC
button and the local username/password form. This is useful during development
or for emergency admin access. Leave it disabled in stricter production
deployments if all users should authenticate through the external provider.

OIDC authenticates identity only. Authorization remains local:

```text
OIDC subject/email -> COHORTome user -> role/groups -> dataset access
```

An OIDC user must map to an enabled local COHORTome user by
`external_subject` or email. Automatic user provisioning is intentionally not
enabled.

## Roles versus groups

The app uses both concepts, but for different purposes.

### Role

A role controls application-level privileges such as:

- whether a user can see `Data Administration`
- whether a user can see `Users`

Current important role:

- `admin`

The app also accepts membership in the `admin` group as an administrative path for UI visibility and backend admin endpoints.

### Group

A group controls dataset access through dataset policy.

Examples:

- `cnag`
- `admin`

Groups are the preferred way to grant dataset access at scale.

## Recommended policy model

The intended operating rule is:

- groups first
- direct user access as exception

In practice that means:

- grant datasets to groups whenever possible
- use direct allowed users for special cases

## Groupless users

A user without groups is still valid.

Such a user:

- gets no dataset access through groups
- may still gain access through:
  - broad dataset visibility
  - direct `allowed_users`

This matters because not every local user needs to belong to an organizational group.

## What the UI can edit

### Dataset policy

`Data Administration` can edit:

- visibility
- allowed groups
- allowed users

### Users

The `Users` tab can now manage local users directly:

- create local users
- set optional email addresses for self-service password reset
- edit display name
- edit role
- edit groups
- enable or disable accounts
- reset passwords
- delete local users

The `Settings` panel shows the current user's authentication summary:

- signed-in identity
- actual login method for the current session
- configured provider
- local fallback state
- password-reset availability
- email, role, and groups

When `COHORTOME_AUTH_MODE=oidc` and `COHORTOME_AUTH_LOCAL_FALLBACK=true`, a user who signs in
with the local form is shown as local fallback for that session. This avoids the
misleading impression that an OIDC login happened when it did not.

Current protections include:

- no deleting the currently signed-in user
- no disabling the currently signed-in user
- no self-demotion from the current admin session
- no deleting the last enabled admin

## Password reset

Admin password reset is always available in the `Users` tab for local users.

Self-service password reset is optional. It is enabled only when local auth is
enabled and SMTP delivery is configured:

```bash
export COHORTOME_AUTH_MODE=local
export COHORTOME_SMTP_HOST=smtp.example.org
export COHORTOME_SMTP_PORT=587
export COHORTOME_SMTP_FROM=noreply@example.org
export COHORTOME_SMTP_USERNAME=...
export COHORTOME_SMTP_PASSWORD=...
export COHORTOME_SMTP_TLS=true
export COHORTOME_PUBLIC_BASE_URL=https://cohortome.example.org
```

Optional:

```bash
export COHORTOME_PASSWORD_RESET_TTL_MINUTES=60
```

When SMTP reset is configured, the sign-in screen shows `Forgot password?`.
Users can request a reset by username or email. The response is intentionally
generic so that the app does not reveal whether an account exists.

Reset links are one-time use and expire after the configured TTL. Tokens are
stored hashed under:

- `state/auth/password-reset-tokens.json`

Users without an email address, disabled users, and non-local users cannot use
self-service password reset. They still require an administrator reset.

## Admin group direction

The app is moving toward cleaner group-based administration.

That means the long-term model can be:

- the username `admin` is just one user
- real administrative capability can also be granted through the `admin` group

For now, local role-based admin support still exists and is useful during development.

## Future direction

The local auth model is now provider-ready:

- current provider: `local`
- future provider: external identity such as Google OIDC

COHORTome should continue to own authorization concepts such as:

- roles
- groups
- dataset access
- in-app disclosure policy
- AI-provider policy

For production environments with institutional identity management, external
OIDC/SAML/LDAP remains the preferred long-term authentication model. Local SMTP
password reset is intended for controlled deployments that still use local auth.

## Local OIDC development with Dex

Dex is the recommended local OIDC provider for development because it is small
and can run as a disposable container.

Start Dex from the repository root:

```bash
docker compose -f scripts/dev/docker-compose.dex.yml up
```

Start COHORTome in OIDC mode:

```bash
export COHORTOME_AUTH_MODE=oidc
export COHORTOME_OIDC_PROVIDER_NAME=Dex
export COHORTOME_OIDC_ISSUER=http://127.0.0.1:5556/dex
export COHORTOME_OIDC_CLIENT_ID=cohortome
export COHORTOME_OIDC_CLIENT_SECRET=cohortome-secret
export COHORTOME_OIDC_REDIRECT_URI=http://127.0.0.1:8000/auth/oidc/callback
export COHORTOME_AUTH_LOCAL_FALLBACK=true
export COHORTOME_SESSION_SECRET="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
PYTHONPATH=.deps uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

The development Dex config includes one static user:

- email: `manuel.rueda@cnag.eu`
- password: `password`

That email must also exist on the local COHORTome user record, for
example `mrueda` in `state/auth/users.json`.

Production Google or institutional OIDC should use the same app-side variables
with provider-specific issuer, client ID, client secret, and redirect URI.
